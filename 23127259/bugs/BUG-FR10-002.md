# [BUG-FR10-002] Canceled terminal order can be transitioned to delivered

## 1. Summary & Defect Overview
An order that has entered the terminal `canceled` state can be resurrected and transitioned to `delivered` by an Admin via `PUT /api/admin/orders/:id/status` with body `{"status":"delivered"}`. The SUT accepts the request with HTTP `200 OK` and mutates the order status from `canceled` to `delivered`.

---

## 2. Requirement / Oracle Violation
- **Normative Source:** EShop SRS Document Section 4.10 (State Transition Constraints) & Level 2 FSM State Machine Definition.
- **Normative Rule:** `canceled` is a terminal sink state in the order state machine. Once an order is canceled, no further state transitions are permitted under any circumstances.
- **Expected Behavior:** `PUT /api/admin/orders/:id/status` with body `{"status":"delivered"}` on a `canceled` order must be rejected with a `4xx` Client Error (e.g., `400 Bad Request` or `422 Unprocessable Entity`), and the order state must remain `canceled`.
- **Actual Behavior:** SUT returns HTTP `200 OK` and mutates the order status to `delivered`.

---

## 3. Severity & Impact
- **Severity:** **HIGH**
- **Impact:** Lifecycle integrity violation. Terminal orders (already refunded or discarded) can be improperly fulfilled and marked as delivered, corrupting audit trails, revenue reporting, and inventory tracking.

---

## 4. Preconditions & Test Environment
- **Host Under Test:** `http://localhost:3000`
- **Student Identifier:** `X-Student-Id: 23127259`
- **Authenticated Actors:**
  - System Admin: `admin@eshop.com` (`role = 'admin'`)
  - Customer (User A): `user@eshop.com` (`role = 'user'`)
- **Initial Fixture State:** Order placed by User A, transitioned by Admin to `canceled`. Initial state verified via authorized `GET /api/orders/:id` as `'canceled'`.

---

## 5. Steps to Reproduce
1. Authenticate as Admin (`role = 'admin'`) and obtain a valid JWT.
2. Authenticate as User A (`role = 'user'`) and obtain a valid JWT.
3. User A creates a fresh order via `POST /api/checkout` with header `X-Student-Id: 23127259`.
4. Admin transitions the order to `canceled` via `PUT /api/admin/orders/:id/status` body `{"status":"canceled"}`.
5. Verify initial order status via `GET /api/orders/:id` (returns `"status": "canceled"`).
6. As Admin, send mutation request targeting the terminal order:
   ```http
   PUT /api/admin/orders/:id/status HTTP/1.1
   Host: localhost:3000
   X-Student-Id: 23127259
   Authorization: Bearer <adminToken>
   Content-Type: application/json

   {
     "status": "delivered"
   }
   ```
7. Observe HTTP response status and body.
8. Execute authorized query `GET /api/orders/:id` to inspect persisted state.

---

## 6. Expected vs. Actual Result
- **Expected Result:** HTTP `4xx` Client Error; persisted state remains `'canceled'`.
- **Actual Result:**
  - HTTP Status: `200 OK`
  - Response Body: `{"message": "Order status updated", "status": "delivered"}`
  - Persisted state observed via authorized API GET: `'delivered'`
