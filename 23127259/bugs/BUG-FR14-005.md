# BUG-FR14-005: Already-Deleted Category PUT/DELETE Returns False Success

## Severity

**MEDIUM** — Data-integrity defect; the API claims successful
modification/deletion of an entity that no longer exists, contradicting
the basic CRUD contract.

## Requirement Source

- SRS FR-14: Category CRUD operations must reflect actual persisted
  state. A successful response without an actual underlying entity
  violates the CRUD contract.
- API specification §3.4: `PUT /api/categories/:id` updates an existing
  category. `DELETE /api/categories/:id` removes an existing category.

## Security Mapping

SEC-02 (state integrity); secondary FR-14 data-integrity concern.

## Precondition

- Admin account is authenticated with valid JWT.
- A valid category exists and is then deleted in the same scenario.
- The category ID is captured for the subsequent PUT/DELETE attempt.

## Reproduction

1. Login as admin.
2. Create a category with name "ZombieTarget".
3. Capture the new category ID.
4. Delete the category via `DELETE /api/categories/{id}`.
5. Send `PUT /api/categories/{id}` with `{"name":"ZombieResurrected"}`.
6. Send `DELETE /api/categories/{id}` again.
7. Verify via `GET /api/categories`.

## Expected Behavior

The PUT and DELETE on an already-deleted category must not falsely
report success. Any accurate non-success response is acceptable
(exact status is not specified by Level-1).

## Actual Behavior

Both PUT and DELETE on the already-deleted category return **200 OK**
with success-style messages ("Category updated" / "Category deleted"),
even though no entity was actually mutated.

## Verification

Confirmed via Newman Run01 execution of TC-FR14-037 and TC-FR14-038:
both responses carried the success-style body but the entity was
absent before and after the call.
