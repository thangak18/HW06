# BUG-FR14-001: Regular User Can Mutate Category Data (RBAC Violation)

## Severity

**HIGH** — Security defect, FR-12 and SEC-03 violation.

## Requirement Source

- SRS FR-12: "Every data-affecting API endpoint must be accessible only by an Admin account."
- SRS SEC-03: "Role-based access control (RBAC) must be enforced on all protected endpoints."
- API specification §3.4: `POST/PUT/DELETE /api/categories` require Admin authentication.

## Security Mapping

SEC-03 (Role-based access control enforcement).

## Precondition

- Regular user account with `role=user` is authenticated.
- The user obtains a valid JWT token through normal login.

## Reproduction

1. Login as regular user `test@eshop.com` / `Test1234!`
2. Obtain JWT token.
3. Send `POST /api/categories` with `Authorization: Bearer {userJWT}` and `{"name": "UserCreatedCategory"}`.
4. Send `PUT /api/categories/2` with same user token.
5. Send `DELETE /api/categories/2` with same user token.

## Expected Behavior

Each request should return a **4xx** error (401 Unauthorized or 403 Forbidden) because regular users must not have data-mutation access per FR-12 and SEC-03.

## Actual Behavior

All three requests return **200 OK** with mutation success messages:

```
POST /api/categories → 200 {"message":"Category created","id":...}
PUT /api/categories/2 → 200 {"message":"Category updated"}
DELETE /api/categories/2 → 200 {"message":"Category deleted"}
```

The API does not validate the `role` claim from the JWT. Any authenticated user can mutate category state regardless of their role.

## Verification

- Fresh Newman Run01: TC-FR14-012, TC-FR14-013, TC-FR14-014 all fail with `expected 200 to be at least 400`.
- The categories created/modified/deleted by regular users are persistent and visible through subsequent `GET /api/categories` calls.
