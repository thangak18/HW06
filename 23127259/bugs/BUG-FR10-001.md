# [BUG-FR10-001] Owner can cancel an order after it enters shipping state

## 1. Summary & Defect Overview
An order owner (customer with `role = 'user'`) is permitted to cancel an order that has already transitioned into the `shipping` lifecycle state by calling `PUT /api/orders/:id/cancel`. The SUT accepts the request with HTTP `200 OK` and mutates the persisted API-visible order status from `shipping` to `canceled`.

---

## 2. Requirement / Oracle Violation
- **Normative Source:** EShop SRS Document Section 4.10 (Order Lifecycle & State Transitions) & Assignment Notes FR-10.
- **Normative Rule:** Customer self-service cancellation is strictly permitted ONLY while the order is in `pending` or `confirmed` status. Once the order enters `shipping` (dispatched/in-transit), customer cancellation is strictly prohibited.
- **Expected Behavior:** `PUT /api/orders/:id/cancel` on a `shipping` order must be rejected with a `4xx` Client Error (e.g., `400 Bad Request` or `422 Unprocessable Entity`), and the persisted API-visible order state must remain `shipping`.
- **Actual Behavior:** SUT returns HTTP `200 OK` and mutates the order status to `canceled`.

---

## 3. Severity & Impact
- **Severity:** **HIGH**
- **Impact:** Critical business logic failure. Customers can unilaterally cancel orders that are already physically in transit with delivery couriers, leading to logistics desynchronization, financial loss, and inventory discrepancies.

---

- **Host Under Test:** `http://localhost:3000`
- **Student Identifier:** `X-Student-Id: 23127259`
- **Authenticated Actors:**
  - System Admin: `admin@eshop.com` (`role = 'admin'`)
  - Order Owner (User A): `user@eshop.com` (`role = 'user'`)
- **Initial Fixture State:** Order placed by User A, advanced by Admin to `confirmed`, and advanced by Admin to `shipping`. Initial state verified via authorized `GET /api/orders/:id` as `'shipping'`.

---

## 5. Steps to Reproduce
1. Authenticate as User A (`role = 'user'`) and obtain a valid JWT.
2. Authenticate as Admin (`role = 'admin'`) and obtain a valid JWT.
3. User A creates a fresh order via `POST /api/checkout` with header `X-Student-Id: 23127259`.
4. Admin transitions the order to `confirmed` via `PUT /api/admin/orders/:id/status` body `{"status":"confirmed"}`.
5. Admin transitions the order to `shipping` via `PUT /api/admin/orders/:id/status` body `{"status":"shipping"}`.
6. Verify initial order status via `GET /api/orders/:id` (returns `"status": "shipping"`).
7. As User A (Order Owner), send cancellation request:
   ```http
   PUT /api/orders/:id/cancel HTTP/1.1
   Host: localhost:3000
   X-Student-Id: 23127259
   Authorization: Bearer <userAToken>
   Content-Type: application/json

   {}
   ```
8. Observe HTTP response status and body.
9. Execute authorized query `GET /api/orders/:id` to inspect persisted API-visible state.

---

## 6. Expected vs. Actual Result
- **Expected Result:** HTTP `4xx` Client Error; persisted API-visible state remains `'shipping'`.
- **Actual Result:**
  - HTTP Status: `200 OK`
  - Response Body: `{"message": "Order canceled successfully"}`
  - Persisted state observed via authorized API GET: `'canceled'`
