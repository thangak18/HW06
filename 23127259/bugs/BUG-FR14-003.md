# BUG-FR14-003: Nonexistent and Already-Deleted Category IDs Report False-Success for PUT/DELETE

## Root-Cause Consolidation Note (2026-09-03)

This bug report now also covers the behavior originally filed separately as
BUG-FR14-005 (`TC-FR14-037/038`). Both test groups exercise the same
Level-1 oracle:

> "Any status is allowed, but the API must not falsely report successful
> modification/deletion of no existing entity."

The runtime evidence shows the same backend defect (success-style 200 OK
response payload for nonexistent IDs **and** for already-deleted IDs).
Therefore the project records **4 unique root causes** for FR14 (this
report plus BUG-FR14-001 / #32, BUG-FR14-002 / #33, BUG-FR14-004 / #36),
not 5.

GitHub Issue [#37](https://github.com/thangak18/HW06/issues/37) is
preserved historically and closed as a duplicate of [#34](https://github.com/thangak18/HW06/issues/34).

## Severity

**MEDIUM** — CRUD integrity violation; misleading API responses.

## Requirement Source

- API specification §3.4: `PUT /api/categories/:id` and `DELETE /api/categories/:id` operate on existing entities.
- Implicit CRUD contract: a successful response implies the operation actually modified an existing entity.

## Security Mapping

Not directly applicable to a security classification, but the false-success behavior can mislead downstream consumers and security-audit tooling.

## Precondition

- Admin account is authenticated with valid JWT.
- Target ID `99999` does not exist.
- Lifecycle category ID has already been deleted.

## Reproduction

1. Login as admin.
2. Send `PUT /api/categories/99999` with `{"name":"GhostCategory"}`.
3. Send `DELETE /api/categories/99999`.
4. Send `PUT /api/categories/{deletedId}` after a prior DELETE on the same ID.
5. Send `DELETE /api/categories/{deletedId}` for an already-deleted ID (double-delete).

## Expected Behavior

The API should not falsely report success when no entity is actually mutated or deleted. Any accurate status (e.g., 404 not found, 410 gone) is acceptable. The response must not claim a successful mutation that did not occur.

## Actual Behavior

All four operations return **200 OK** with success messages even though no entity was actually mutated or deleted:

```
PUT /api/categories/99999 → 200 {"message":"Category updated"}
DELETE /api/categories/99999 → 200 {"message":"Category deleted"}
PUT /api/categories/{deletedId} → 200 {"message":"Category updated"}
DELETE /api/categories/{deletedId} → 200 {"message":"Category deleted"}
```

The implementation responds with a generic success message regardless of whether a row was actually modified.

## Verification

Subsequent `GET /api/categories` does not show the new category that PUT claimed to update.
