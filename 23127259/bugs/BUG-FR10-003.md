# [BUG-FR10-003] Regular customer can mutate order status through Admin API

## 1. Summary & Defect Overview
Regular customer accounts (`role = 'user'`) can directly invoke administrative order management endpoints (`PUT /api/admin/orders/:id/status`) and successfully mutate order lifecycle states. The endpoint performs zero role-based access control (RBAC) validation, accepting any valid JWT regardless of role permissions.

---

## 2. Requirement / Oracle Violation
- **Normative Source:** EShop SRS Document Section 4 & Assignment Notes Pool C / Security Category `SEC-03` (Role-Based Access Control).
- **Normative Rule:** All administrative API endpoints under `/api/admin/*` must strictly verify that the authenticated identity possesses `role = 'admin'`. Requests bearing standard customer tokens (`role = 'user'`) must be rejected.
- **Expected Behavior:** `PUT /api/admin/orders/:id/status` executed with a customer token must be rejected with HTTP `403 Forbidden` (or `401 Unauthorized` / `4xx`), and the order state must remain unchanged.
- **Actual Behavior:** SUT returns HTTP `200 OK` and mutates the order status across all valid state transitions (`pending -> confirmed`, `pending -> canceled`, `confirmed -> shipping`).

---

## 3. Severity & Impact
- **Severity:** **CRITICAL**
- **Impact:** Privilege Escalation / Complete Authorization Bypass (CWE-269 / CWE-285). Any authenticated customer can arbitrarily advance or cancel any order in the entire system, manipulate order fulfillment, and disrupt business operations.

---

## 4. Preconditions & Test Environment
- **Host Under Test:** `http://localhost:3000`
- **Student Identifier:** `X-Student-Id: 23127259`
- **Authenticated Actors:**
  - Customer (User A): `user@eshop.com` (Verified JWT claim: `role = 'user'`)
  - System Admin: `admin@eshop.com` (Verified JWT claim: `role = 'admin'`)
- **Initial Fixture State:** Fresh disposable orders created by User A in `pending` and `confirmed` states.

---

## 5. Steps to Reproduce
1. Authenticate as Customer User A (`user@eshop.com`) via `POST /api/login`.
2. Verify decoded JWT payload contains `role: "user"`.
3. User A creates a fresh order via `POST /api/checkout` with header `X-Student-Id: 23127259` (Order ID: `97`, state: `pending`).
4. Using User A's token (`role = 'user'`), send an Admin mutation request:
   ```http
   PUT /api/admin/orders/97/status HTTP/1.1
   Host: localhost:3000
   X-Student-Id: 23127259
   Authorization: Bearer <userAToken>
   Content-Type: application/json

   {
     "status": "confirmed"
   }
   ```
5. Observe HTTP response status and body.
6. As Admin, execute authorized query `GET /api/orders/97` to inspect persisted state.
7. Repeat with cancellation transition `pending -> canceled` on a fresh order (Order ID: `98`) with User A's token.

---

## 6. Expected vs. Actual Result
- **Expected Result:** HTTP `403 Forbidden` / `4xx`; persisted state remains `'pending'`.
- **Actual Result:**
  - HTTP Status: `200 OK`
  - Response Body: `{"message": "Order status updated", "status": "confirmed"}`
  - Persisted state observed via authorized API GET: `'confirmed'` (and `'canceled'` on Order `98`)

---
